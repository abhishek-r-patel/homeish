## 1. Problem, Value Proposition, Target Users

### 1.1 Problem

Residential societies/apartments run on a mix of paper registers, WhatsApp groups, spreadsheets and phone calls. This causes:

- Unverified visitors/deliveries entering premises; no audit trail.
- Residents unaware of who is at the gate.
- Manual, error-prone maintenance billing and poor dues collection.
- Staff (maids, drivers, cooks) attendance and entry untracked.
- Service complaints lost in chat threads; no accountability or SLA.
- Housekeeping consumables and AMC (annual maintenance contracts) tracked ad hoc, leading to lapses and expiries.
- Committee has no single view of operations.

### 1.2 Value Proposition

One multi-tenant SaaS app where every society stakeholder (resident, guard, committee, admin, housekeeping supervisor, vendor) does their daily society tasks in one place, with a **modular** design so each society only pays for/uses what it needs, and the product owner (developer/superadmin) can enable or disable modules per society.

### 1.3 Target Users

| User                       | Description                                                            |
| -------------------------- | ---------------------------------------------------------------------- |
| Resident (Owner / Tenant)  | Lives in a unit; approves visitors, pays dues, raises requests         |
| Security Guard             | At gate; logs visitors/deliveries/staff entry                          |
| Society Admin / Manager    | Day-to-day operations, billing, vendors                                |
| Committee Member           | Oversight, approvals, reports                                          |
| Housekeeping Supervisor    | Manages inventory consumption/stock                                    |
| Domestic Staff / Visitor   | Not app users in MVP (identified via entries/passes only) — **[A-01]** |
| Platform Owner (Developer) | You; configures societies, modules, views logs                         |

### 1.4 Market Assumptions

- **[A-02]** Initial market: India (INR, +91 phone numbers, GST-relevant invoices, UPI payments).
- **[A-03]** Society size: 50–1,500 units; single society may have multiple towers/blocks.
- **[A-04]** Smartphone usage is universal among residents; guards use a shared or dedicated Android device/tablet.

## 2. Product Principles

1. **Modular**: every feature area is a module that can be enabled/disabled per society; disabled modules are invisible and inaccessible (UI and API).
2. **Multi-tenant by default**: every record belongs to one society; no cross-society data access.
3. **Simple first**: smallest workflow that solves the problem; no configurability that isn't required.
4. **Debuggable**: every failure is logged with context so the platform owner can trace it.
5. **Auditable**: sensitive actions (money, entry, role changes) leave an audit record.

### 4.1 Features and Functional Requirements

**Authentication & Accounts**

- `CORE-1` Users sign in with **email + one-time code (OTP) sent by email** in MVP. **[D-03 — Approved 2026-11-09]** The login system must be built so these can be added later **without changing user data**: mobile + OTP, email + password, mobile + password, and social login (e.g., Google). The email address is the user's unique identity; a mobile number is an optional profile field. **[A-34, A-35]**
- `CORE-2` Session persists on device until logout or expiry (**[A-06]** 30 days; guards: 12-hour shift sessions configurable later, not MVP).
- `CORE-3` A user can belong to multiple societies (e.g., owner in two) and switch between them. **[A-07]**
- `CORE-4` Developer/Superadmin sign in via separate login (email + password + TOTP MFA) at a separate URL. **[D-04 — Approved 2026-11-09]**

**Society & Structure**

- `CORE-5` Developer creates a society with: name, address, city, contact, currency (default INR), logo. All societies use India Standard Time (`Asia/Kolkata`). Support for other timezones is deferred to a future Pro feature.
- `CORE-6` Society structure: Society → Blocks/Towers (optional) → Units (flat/house number, floor, type, area sq ft optional).
- `CORE-7` Admin can add/edit/deactivate blocks and units; bulk import units via CSV (MVP).

**Residents & Membership**

- `CORE-8` Unit has occupants with relationship type: Owner, Tenant, Family Member. One **primary contact** per unit.
- `CORE-9` Admin can invite a resident by email address to a unit; or resident self-registers using the **society code** shared by the admin (a rotatable code that can be switched off; it lets them pick their unit without exposing the list of societies) → admin approves. **[D-05 — Approved 2026-11-09; API APD-1]**
- `CORE-10` Admin can deactivate/move out a resident; their access is revoked immediately; historical records retained.
- `CORE-11` Bulk resident import via CSV (MVP).

**Roles & Permissions** — see Section 8.

**Notifications**

- `CORE-12` Channels in MVP: in-app notification inbox, phone push notification, and email (login codes, receipts, developer alerts). SMS/WhatsApp is post-MVP. **[D-06 — Approved 2026-11-09]** If a resident does not respond to a push alert, the guard sees "No response" and can call the resident (VIS-4).
- `CORE-13` In-app notification inbox per user with read/unread.
- `CORE-14` Users can't disable critical notifications (visitor at gate, payment due); no granular preference center in MVP.

**Society Settings (RWA Settings page, admin-editable)**

- `CORE-16` **Gate login mode** (admin chooses): (1) **Individual guard accounts** — each guard has their own email and signs in with it (default); or (2) **Shared gate account** — one shared email for all guards, where each guard identifies themselves when they start a shift or log an entry, so each entry still records who handled it. The admin also chooses _how_ guards identify themselves: **pick their name** from the guard list, or enter a **personal PIN** (stored only as a hash, attempts rate-limited). **[D-30 — Approved 2026-11-09; A-31]**
- `CORE-17` Other society profile values (name, address, contact, logo, and the society's custom label for "Unit") are editable by admin as listed in CORE-5. Timezone is fixed to IST. The custom label is 1–24 letters or spaces and defaults to "Unit". Module settings follow MOD-3 unless a module section says admin-editable (e.g., billing UPI details, BIL-15). Every change is audit-logged. **[DD-05 — amended 2026-11-21]**
- `CORE-18` Users may choose the Homeish font style (Nunito for body text and Quicksand for headings) or their device's default font. The preference is saved to their account and follows them across devices. **[DD-02 — amended 2026-11-20]**

**Module Registry & Developer Config** (developer-only)

- `MOD-1` Developer config pages list all modules per society with an on/off toggle.
- `MOD-2` Disabled module: nav items hidden, API endpoints return a "module disabled" response, background jobs for it skip that society, notifications for it stop.
- `MOD-3` Each module may have module-level settings (defined in each module section), editable by developer; selected settings may be exposed to society admins (flag per setting). **[A-08]** MVP: all module settings developer-only unless stated.
- `MOD-4` Disabling a module retains all its data; re-enabling restores access to it.
- `MOD-5` Every toggle/config change is audit-logged (who, when, old → new).
- `MOD-6` Society-level feature flags are stored as data, not code branches per society.

**Platform Subscription (SaaS)**

- `SAAS-1` Each society has a status: Trial, Active, Suspended, Archived. Suspended societies get read-only access. **[D-07 — Approved 2026-11-09]**
- `SAAS-2` Developer manually sets plan/status in MVP. **No** in-app subscription billing/payment from societies in MVP; invoices are handled outside Homeish. The first ten live societies receive Homeish without a subscription charge; hosting costs are separate. The subscription price and offer terms after the first ten will be decided before society eleven is invited. **[D-08, D-33 — Approved 2026-11-09]**
- `SAAS-3` Tenant isolation enforced at data layer for every query.

**Logging, Error Tracking & Observability** (developer-facing)

- `LOG-1` **Error log**: every unhandled/handled server error and client error is captured with: timestamp, society ID, user ID, role, module, route/action, request ID, error message, stack trace, app version, device/browser info, severity.
- `LOG-2` Every user-facing error displays a short **reference ID** that maps to the log entry so the user can report it and the developer can find it.
- `LOG-3` **Developer Log Viewer** page: filter by society, module, severity, date range, user, reference ID; view detail; mark as Resolved/Ignored; search text.
- `LOG-4` **Audit log** (separate from error log): who did what, when, on what entity, before/after values for sensitive actions (role changes, module toggles, payments, fines, resident approvals, visitor override, bill generation, data exports).
- `LOG-5` Logs never store secrets, OTPs, full payment credentials, or full personal data beyond what's required (mask phone, no document images in logs).
- `LOG-6` Log retention: **[A-09]** error logs 90 days, audit logs 2 years (configurable by developer).
- `LOG-7` Critical-severity errors trigger an alert to developer by email. **[D-09 — Approved 2026-11-09]** Use Sentry plus an app-level log table for tenant-specific audit; do not build an alerting engine.
- `LOG-8` Request ID propagated across client → server → third-party calls for tracing.

**Data Export**

- `CORE-15` Admin can export lists (residents, payments, visitors) to CSV, subject to role permission; exports are audit-logged.

## 5. Module Requirements

### 5.1 Visitor Management (`visitor`)

**Purpose**: Control and record who enters the society and obtain resident consent.

**Journeys**

1. _Walk-in visitor_: Guard logs visitor (name, phone, purpose, unit, optional photo, vehicle no.) → resident gets push notification → approves/denies → guard allows/denies → guard marks check-out.
2. _Pre-approved visitor_: Resident creates an invite (name, date/time window, optional vehicle) → system generates a 6-digit code/QR → guard validates at gate → auto-checked-in, resident notified.
3. _Frequent visitors_ (guest, relative): Resident saves as "frequent" for faster pre-approval. **[A-10]** Originally P2; delivered in MVP+ (2026-11-14): residents save, pre-approve from and remove frequent visitors on the visitors page.

**Functional Requirements**

- `VIS-1` Guard can create a visitor entry: name, mobile, purpose (list: Guest, Cab, Service, Official, Other), unit, vehicle number (optional), number of people, photo (optional).
- `VIS-2` System notifies all active occupants flagged "approver" for that unit. First response wins. **[A-11]**
- `VIS-3` Resident can Approve or Deny; Deny requires no reason.
- `VIS-4` If no response within X minutes (default 3, developer-configurable), the guard sees "No response" and can call the resident (phone dial link). If the society setting allows it, the guard may then mark "Allowed by guard — no response" with a required reason and audit entry. **[D-10 — Approved 2026-11-09]**
- `VIS-5` Resident can pre-approve a visitor with a valid window (from/to). System generates a one-time 6-digit code and a QR encoding that same code. A guard may scan the QR or enter the code manually. **[D-11 — Approved 2026-11-09]**
- `VIS-6` Guard can enter a code to validate and check in a pre-approved visitor; invalid/expired code shows clear error.
- `VIS-7` Guard marks visitor check-out; entry status lifecycle: `Pending → Approved/Denied/Expired → Checked-in → Checked-out`.
- `VIS-8` Resident sees visitor history (own unit). Guard sees today's log for the society. Admin sees all with filters (date, unit, status).
- `VIS-9` Overstay highlight: visitors checked in longer than N hours (default 12) shown as "Still inside" on the admin dashboard.
- `VIS-10` Blacklist: Admin can add a phone number to society blacklist; guard sees a warning when matched (MVP: warn only). **[A-12]**

**Module settings**: approval timeout, overstay hours, photo required (yes/no), guard-override allowed (yes/no).

**User Stories**

- As a guard, I log a visitor in under 30 seconds.
- As a resident, I approve a visitor from the notification without opening the full app.
- As a resident, I pre-approve my guest and share a code.
- As an admin, I view who entered on a specific date.

**Acceptance (sample)**

- Given a visitor entry for Unit A-101, when the resident approves, the guard device shows "Approved" within 5 seconds (p95) of approval.
- Given an expired pre-approval code, when the guard enters it, the system rejects it and logs the attempt.

### 5.2 Delivery Management (`delivery`)

**Purpose**: Track parcels/food deliveries and reduce gate friction.

**Functional Requirements**

- `DEL-1` Guard logs a delivery: company/platform (list + other), delivery person name (optional), unit, type (Food, Parcel, Grocery, Other), optional photo.
- `DEL-2` Resident notified; options: **Allow at gate/Send inside**, **Leave at gate/security desk**, **Deny/Return**.
- `DEL-3` Resident can set a standing preference per unit: "Always allow", "Always leave at gate", "Ask me" (default). **[A-13]**
- `DEL-4` Resident can pre-announce an expected delivery (platform, window) so the guard sees it as expected. **[A-14]** Originally P2; delivered in MVP+ (2026-11-14): window up to 24 hours, residents can cancel, guards see a read-only "Expected deliveries" list.
- `DEL-5` For parcels left at the security desk: status `Received → Collected` and resident marks/guard marks collection, with timestamp. Uncollected parcels older than N days are listed for the guard/admin (default 3).
- `DEL-6` Delivery history per unit; society-wide log for guard/admin.
- `DEL-7` Delivery statuses: `Pending response → Allowed / Left at gate / Denied → Collected / Closed`.

**Module settings**: response timeout, uncollected-parcel threshold days, enable "leave at gate" option.

**User Stories**

- As a resident, I tell the guard to keep my parcel at the gate while I'm away.
- As a guard, I see which parcels are still uncollected.

### 5.3 Maintenance, Fines & Payments (`billing`)

**Purpose**: Generate dues, collect payments, track overdue, and give residents/committee transparency.

**Concepts**

- **Charge Type**: e.g., Monthly Maintenance, Sinking Fund, Parking, Water, One-time charge.
- **Bill/Invoice**: a due for a unit for a period, containing one or more charge lines.
- **Fine**: a penalty added to a unit's ledger (manual by admin, or auto late fee).
- **Payment**: paid directly to the society's UPI account and submitted by the resident for admin confirmation, or recorded by the admin (cash/cheque/bank transfer/UPI).
- **Unit Ledger**: running statement of debits (bills/fines) and credits (payments).

**Functional Requirements**

- `BIL-1` Admin defines charge types with a calculation method: **Fixed per unit**, **Per sq ft**, **Custom per unit** (manual amount), or **Percentage of Maintenance**. The percentage is greater than 0% and at most 100%, with up to two decimals. The admin selects an active, non-percentage base charge in the same society. Use the already-published base for the same unit and month or a base line to be generated in the same run. If it is not applicable, omit the percentage line; if it is required but missing, stop and explain. Apply society rounding and show, but do not bill, percentage lines that round to zero. Published bills stay unchanged. **[D-12 — P37 update approved 2026-11-20]**
- `BIL-2` Admin generates bills for a period (monthly default) for all/selected units; preview before confirming; generation is idempotent (no duplicates for same unit + period + charge type).

### 5.9 Amenity Booking (`amenity`) — P2-5

Identity is shown only when Directory is enabled and its resident visibility preference permits it; otherwise the calendar falls back to availability-only. The existing booking picker remains anonymous for other units. No phone, email, guest count, rules or cancellation reason is exposed. Same-amenity overlapping confirmed bookings are shown only as a data-integrity warning; booking rules and the database exclusion constraint remain authoritative. Owner UAT and live enablement remain pending.

A society setting defaults to availability-only and lets an admin select availability, booker name, or booker name and unit. Resident identity details appear only when Directory is enabled and the person's resident visibility preferences permit them; otherwise the entry is availability-only. The calendar exposes no contact details, guest counts, rules or cancellation reasons. An unexpected same-amenity overlap is an integrity warning, not a booking override.

**P35.8–P35.9 amenity deposits (D-84 proposed 2026-11-23; coding not yet approved).** These apply only to refundable deposits for amenity bookings, not P39 fixed deposits. Deposits are off by default. When enabled for an amenity, the admin sets a standard amount and whether payment is required before confirmation. In the normal `per_amenity` society mode, a required deposit reserves the slot while awaiting payment; an admin records externally completed receipts, and the booking confirms only when the full amount is received. Partial receipts are allowed. A society admin may instead select `immediate` confirmation in Amenity settings; bookings then confirm immediately and the configured deposit remains outstanding. The existing amenity fee stays separate.

- `AMN-5` (P35.8) Admins configure an optional refundable deposit amount per amenity. New bookings snapshot the amount and requirement; later configuration changes do not alter existing bookings. An admin may override the amount, with a reason, only while a booking is awaiting deposit and before any receipt. Once confirmed, its terms are locked. Under society-wide `immediate` mode, the amenity's configured amount is used and per-booking overrides are unavailable.
- `AMN-6` (P35.9) Admins record actual receipts and refunds made outside Homeish, and deductions after the booking with a reason and evidence. Multiple partial receipts and refunds are allowed; refunds plus deductions cannot exceed receipts. Cancelling a booking returns all deposit money actually received without a deduction; the existing full credit for the amenity fee remains a separate unit-ledger action. No payment gateway or automatic refund is included.
- **Accounts treatment:** P16 records deposit receipts and refunds as cash movements that are neither income nor expense. A deduction kept by the society is a separate income reclassification linked to the deposit history; it is not a second cash receipt. The P16 cash balance includes held money, while income/expense reports distinguish it from cash movements. P41 statements show held-deposit receipts/refunds separately and identify retained amounts as a non-cash reclassification. This is a narrow proposed extension to D-39, not a liability ledger or balance sheet; an accountant should review it before real use. P27 is unchanged.
- **Access and records:** admins manage; committee members read; active residents of the booking's unit see that unit's deposit breakdown and evidence. Other residents and guards see none. Records and evidence are retained permanently. Turning deposits off prevents new deposit bookings but does not erase existing records; Amenity and Accounts cannot be disabled while a deposit remains unsettled.

#### 5.10.1 Society Expenses & Accounts (`expense`) — P3-1

Simple society bookkeeping, not double-entry accounting (D-39). **P16 kickoff decisions (approved 2026-11-14):** default categories are repairs, utilities, staff, housekeeping, security, AMC, insurance/taxes, administration, events and other; accounts include cash and one or more banks with opening balances; committee approval is required above ₹50,000, configurable by society admins; closed months are locked, with admin reopening only by an audited reason; financial year is 1 April–31 March. D-84 proposes a narrow, separate cash-book treatment for refundable amenity deposits; current behavior remains unchanged until that proposal is approved for coding.

- `EXP-1` Admin records expenses with date, category, payee, amount (paise), payment mode (cash, bank, UPI, cheque), reference and an optional receipt (JPEG/PNG/PDF).
- `EXP-2` Expense categories are society-defined, with defaults created on enable.
- `EXP-3` Cash and bank books: named accounts with an opening balance, append-only entries and reversal instead of deletion.
- `EXP-4` Confirmed `billing` payments appear as income automatically when billing is enabled; other income (donations, interest) is entered manually.
- `EXP-5` Reports: income vs expense by month/category, account balances, outstanding dues summary (from billing), CSV and PDF export.
- `EXP-6` Optional committee approval above a society-set amount; committee read-only access otherwise.

**P16 implementation choices (approved 2026-11-15, D-44):** any one committee member other than the person who recorded an expense approves it above the threshold; at or below it, expenses post immediately. Admins choose the account that receives confirmed billing payments as income. Exports are CSV and PDF. Residents see nothing in this module, except the proposed EXP-35 budget summary (D-83). Expenses are not edited; they are rejected or reversed and recorded again. An expense above the threshold stays pending if no other committee member exists.

**P39 accounts additions (D-69 — approved 2026-11-19).** Owner kickoff answers 2026-11-19. EXP-7–EXP-11 are views and registers on top of P16; they do not create, change or delete cash/bank entries. P39.5 adds the fixed-deposit register (EXP-17); P39.7 adds paired own-account transfer entries under D-74 (EXP-20), without full double-entry accounting. Access follows P16 (admins manage, committee read-only, residents none) unless stated.

- `EXP-7` Each cash/bank book row shows a running balance calculated from the opening balance, in date order and then the order entries were recorded. A reversal is its own row on its own date; the original row is unchanged. The balance is calculated, not stored.
- `EXP-8` Every entry has one permanent voucher number based on its direction: money in (including billing payments and reversals of expenses) `RV/<financial year>/<number>` and money out `PV/<financial year>/<number>`, restarting each financial year. Existing entries are numbered once, in date order, when the feature is turned on. A number never changes, and no new financial entry is created.
- `EXP-9` Manual bank reconciliation: admins record statement items (date, reference, party, type, amount) against bank books and mark them matched or cancelled with a reason. Items unmatched for more than 30 days are flagged as old. Differences never post entries; real adjustments use the normal P16 entries.
- `EXP-10` Petty cash: an admin marks one cash account as petty cash and names one app user as its custodian. The custodian sees only the petty-cash view and records physical cash counts (date, counted amount, note); admins can too. The book amount comes from P16 entries; any difference from a count is shown, never posted. Changing the custodian requires a handover count, and the custodian history is kept. A fixed float (imprest) amount is left for a possible future Pro version.
- `EXP-11` The accounts report adds monthly net surplus/deficit and the cumulative figure from the start of the financial year, labelled so it is not mistaken for cash or bank balances. No new P27 metric.

**P39.5 and P40 manual fund tracking (D-73 — approved 2026-11-21, refined by D-74; P39.5/P39.7, P40.1a–P40.7 and the partial P40.8 report are on beta/testdb).** These tools do not establish legal or accounting authority. An admin must acknowledge a warning before use; professional review is recommended rather than an in-app prerequisite. Applicable statutory and bye-law checks, P10 and separate live-release approval still apply. Admins manage the records; committee members read them, except that fixed-deposit references are admin-only. Residents and guards have no general access. The full reconciliation/target P40.8 report is proposed as EXP-36 under D-87; P40.9 is proposed as EXP-30 under D-82.

- `EXP-12` Admins name and maintain society funds. Fund tracking starts off until an admin sets a cutover and opening allocations against the cash/bank book total at the end of the preceding day. The cutover is the first day of a month, and the previous month must be closed before activation (D-74). Named openings may not exceed that total; the remainder is Unallocated. A negative opening total prevents activation until reconciled, without blocking Accounts. Historical entries remain reviewable and do not count twice; new account openings after cutover are Unallocated, not income. Entries can be split only when their allocations total the source entry, and reversals follow the same split. Unmapped historical reversals remain Unallocated until the original is mapped. An admin may set a suggested fund for each expense category and income type; a suggestion is never saved until an admin confirms it, one by one or in bulk (D-74). Backdated changes flag the opening for review; opening corrections and allocation changes retain reasons and history. Reopen a closed month before changing its allocations. Show negative fund balances and warnings, but do not block normal cash-book posting.
- `EXP-13` The existing Billing estimate may group each charge under at most one fund; unmapped charges remain Unallocated. An optional 1–12 month preview repeats the monthly estimate and states that rates and occupancy are assumed unchanged. The preview creates no bill or actual payment allocation. Separately, a confirmed Billing collection in Accounts shows a suggested split that follows the paid bills' charge lines and their funds, in proportion for part payments; rounding leftovers, lines without a charge type or fund and amounts not applied to a bill stay Unallocated. The suggestion is saved only when an admin confirms it (D-74). The original estimate remains usable if Accounts is disabled.
- `EXP-14` Admins may record a unit's corpus event description, fund, date, reported amount, optional concession and reason, and decision reference. Show the recorded amount, linked receipts and remaining amount as a tracker, not a legal debt, bill, unit credit or NOC block. Link portions of existing confirmed Accounts receipts without counting a portion twice or exceeding its fund allocation. An unmatched excess remains unlinked. When the source does not establish a unit, the admin confirms the match. Reversals reduce linked receipts; no link is not proof that no payment was made.
- `EXP-15` Admins record sanctioned work, fund, amount, date, optional validity and a passed Homeish meeting resolution or external decision reference. Actual spending is derived from posted Accounts expenses; links across works cannot exceed the expense's allocation to that fund. Reversals reduce linked spending. Expiry and overruns warn without blocking ordinary expense posting; a changed or unavailable meeting source is flagged. The record is not an approval or proof of authority.
- `EXP-16` Admins configure permitted fund pairs and record transfers with amount, date, reason and a decision reference, including for redevelopment funds. A transfer is equal and opposite between allocations, does not move bank money and cannot exceed the recorded available source-fund balance on its date. Unreconciled deposits are not available for that check. Corrections use reasoned reversals. Neither a configured pair nor a reference proves legal authority.
- `EXP-17` Admins record bank-confirmed fixed-deposit bank, fund, reference, principal, quoted rate, deposit and maturity dates and maturity value. Unknown figures remain unknown. A worklist shows deposits due within 30 days or past maturity; maturity does not mean payment. Each deposit links to one Accounts deposit account (EXP-20), which holds the actual money; register figures are never added to Accounts totals. A deposit without a linked account is labelled not reconciled, and a linked account whose balance differs from the confirmed principal shows the difference. A renewal records a successor deposit on the same account. No automatic renewal, notification or posting occurs.
- `EXP-18` Record bank-provided interest, tax withheld and actual credit; calculate gross less withholding when both are known and compare with linked Accounts income, flagging differences. Optional annualised yield is gross interest divided by average balance, multiplied by 12 divided by the number of whole months, then by 100. It is labelled an estimate and available only when inputs are known and valid. No tax rate, automatic posting or accountant approval is implied.
- `EXP-19` An on-screen partial fund report derives available openings and movements from linked sources, explicitly shows Unallocated and unreconciled amounts and does not invent missing figures. Existing Accounts exports remain unchanged. The reconciliation status, statement balances and fund targets are proposed as EXP-36 (D-87).
- `EXP-20` (P39.7; D-74 — contract confirmed at the coding go-ahead) Admins record a transfer between two active accounts of the same society, such as bank to cash, bank to a fixed deposit or a matured deposit back to bank, with date, amount, reference and note. It creates one money-out and one money-in entry with the same date and amount, each with its normal EXP-8 voucher and shown as "Transfer". A transfer counts in account balances, running balances, reconciliation and petty-cash books, but never as income, expense or a category in reports, net flow, exports or dashboard metrics, and it has no fund effect. Reversing a transfer reverses both entries together, with a reason. A new deposit account type holds fixed deposits; it accepts only transfers, interest income and reversals and cannot be used for expenses, Billing income or petty cash. Month locks and account opening dates apply to both entries. This adds no journal entries, general ledger or trial balance.

**P41 financial reports (D-77 — implemented, verified and on beta/testdb 2026-11-22).** P41.1, P41.2 and P41.4–P41.7 are available in the beta code and testdb schema. P41.3 remains blocked for B7. - `EXP-21` (P41.1) A new Accounts **Statements** tab shows two views for a chosen range of up to two years, both downloadable as CSV and PDF.
  - The receipts-and-payments statement lists money held at the start (cash, bank and deposit accounts), opening balances of accounts added in the range, receipts by income type, payments by category, and money held at the end. The lines add up.
  - The month-by-head table lists income types and categories against every month, including empty months. Reversals reduce their head in the month they were made. The PDF prints months in blocks of up to six.
- `EXP-22` (P41.2) A "Financial position summary — not a balance sheet" for a chosen date lists:
  - cash/bank balances by account and their total;
  - fund balances and Unallocated, when fund tracking is active;
  - member dues still owed, when Billing is on;
  - unpaid vendor bills, when Vendors is on;
  - fixed deposits from the register, shown separately and never added to totals.

  Dues and vendor bills appear only for today; for a past date they show "Not available for a past date". Each line names its source; a missing source shows "Not available", never zero. There are no fixed assets, depreciation, accruals, net-worth line or solvency/compliance wording.

- `EXP-23` (P41.4) A five-financial-year comparison shows income and expenditure by head for the current year to date and the four previous years. Years before the books started show "Not available"; the first partial year is labelled "part year". Percentage change appears only between complete years when the earlier value is positive; otherwise it shows a dash. The year-to-date column has no percentage change.
- `EXP-24` (P41.5) A non-certifying audit tracker opens only after an admin acknowledges, once per society, that it does not replace an auditor, accountant or legal advice. Per financial year, admins record:
  - the auditor and firm, appointment date and decision reference or document;
  - queries with number, date, area, question, an assignee from the society's admins or committee, due date, response and response date;
  - report received, placed-before-AGM and filed dates;
  - the opinion copied from the report (unmodified, qualified, adverse, disclaimer or other) with its text;
  - objections with owner, due date, correction note and evidence document.

  Statuses (open, answered, overdue, resolved) are calculated from recorded facts. Automatic year-end checks show whether all twelve months are closed, any bank statement item has been unmatched for more than 30 days, every fixed deposit is linked and reconciled, and a petty-cash count is dated 25 March–7 April. Records are kept permanently: edits keep earlier values and nothing is deleted. Committee members read only. Auditors get no app access. There are no notifications, generated opinions, certifications, submissions or postings.

- `EXP-25` (P41.6) An AGM report draft for a chosen financial year assembles the year's finances (income and expenditure plus receipts and payments), the multi-year comparison, funds, audit status and opinion, the year-end financial-position summary, and up to 10 admin-written plain-text sections. Each section title is up to 120 characters and each body up to 10,000. All sections are on by default; admins switch them off in the society's Accounts settings. Every figure names its source and year. The draft is labelled "Draft — not a statutory report", uses the EXP-24 acknowledgement, and is viewed by admins and committee and downloaded as PDF. It is never published in the app and contains no member-level data.
- `EXP-26` (P41.7) The Statements tab adds four figures:
  - average monthly expenditure over the last 12 complete months, or fewer with the count stated;
  - months of spending covered by current cash and bank balances, "Not available" when the average is zero;
  - each category's share of expenditure in the range;
  - change in income and expenditure against the same dates a year earlier, shown as a dash when the earlier value is not positive.

  They appear only in Accounts, never on the P27 dashboard, and accept no manual targets, weights or scores.

**P42 expense control additions (D-80 — approved for local coding 2026-11-23; not released).** EXP-27–EXP-29 cover P42.1, P42.3 and P42.4. P42.2 budget alerts remain blocked for B7. None of these features creates, changes or deletes an Accounts entry, bill, budget, fund allocation, vendor payment or contract, and none adds an approval step (D-44 and D-54 unchanged). Access follows P16 unless stated: admins manage, committee read-only, residents and guards none. The existing Reports page, Statements tab, their exports and the P27 dashboard are unchanged.

- `EXP-27` (P42.1) Each expense category may hold four optional details:
  - a group of up to 60 characters, typed by an admin, with existing groups suggested and matched ignoring capitals;
  - a cost nature: `Fixed`, `Variable` or `Periodic`;
  - an owner, who must be an active admin or committee member when saved; if they later lose that role, the name stays, marked "no longer an admin or committee member";

The details appear on the category list and as filters in the vendor spend report. No budget, year-to-date, percentage or alert field is added.

- `EXP-28` (P42.3) A read-only **vendor spend report** in Accounts covers any range of up to 24 months, defaulting to the current financial year. It uses posted expense payments less their reversals and excludes own-account transfers and income.
  - **Matching order:** a P47.7 bill-payment link counts for its linked amount. Then an admin-confirmed payee mapping applies. Anything left is shown under the typed payee as "Not linked to a vendor".
  - **Payee mappings:** an admin maps a typed payee, matched ignoring capitals and extra spaces, to one vendor. The mapping applies to past and future posted expenses with that payee. Removing it needs a reason and keeps the history, and committee can view mappings. An unmapped payee with an exact vendor-name match is shown only as a suggestion until an admin confirms it.
  - **Figures:** for each vendor or payee, the total, share of the range's spending, active months, average per active month, a month-by-month table and a category breakdown. The report can be filtered by category, group and cost nature, and it reconciles to the Accounts expense total for the range.
  - **High share:** shown when a vendor or payee is 40% or more of the range's spending, labelled "a reporting signal, not a finding".

  - **Realised to date:** the total of records that are not voided, always shown separately from the expected saving.
  - **No financial effect:** estimates and statuses create no income, expense reduction, budget change, contract change or Accounts entry. The tracker is on screen only, with no downloads, and all history is kept.

**P40.9 repair forecast (D-82 — implemented and locally verified 2026-11-23; not released).** EXP-30 covers P40.9 inside Accounts (`expense`), which must be enabled; fund tracking (EXP-12) is needed only for the fund gap.   - **10-year table:** for each of the current and next nine financial years, each due item's estimated cost is today's cost × (1 + inflation %)^(years from now), rounded to the rupee. An item repeats within the 10 years when its cycle allows. Every figure is labelled "Estimate".

**P41.3, P42.2 and P42.5 budgets (D-83 — approved for local coding 2026-11-23).** P42.5 (EXP-31/EXP-32) and P41.3 (EXP-33/EXP-35) are implemented and locally verified; P42.2 remains unstarted. EXP-31–EXP-35 cover a limited budget plan inside Accounts (`expense`), which must be enabled. This changes GAP-M13-01 from Option A to Option B: the budget is a separate plan; actuals come from posted Accounts entries plus, once D-84/P35.8–P35.9 is implemented, retained amenity-deposit deductions as non-cash Other income. Admins manage; committee members read; residents see only the EXP-35 summary; guards and housekeeping supervisors have no access. There are no growth-rate proposals or delegated spending authority (Option C was not chosen).

- `EXP-31` (P42.5) **Yearly budget.**
  - **Year and states:** one budget per society for each financial year (April–March), `Draft` or `Approved`. An admin can discard a draft with a reason; an approved budget is never deleted.
  - **Heads:** each expense category, plus four types of money coming in: maintenance collections (confirmed Billing payments), donations, interest and other income. Amounts are whole rupees, zero or more.
  - **Starting figures:** blank, or **Copy last year**, which fills each head with last financial year's actual figures net of reversals. Under proposed D-84, retained deposit deductions are included in Other income; held receipts/refunds are not budget income. An optional increase or decrease from −50% to +100% (up to one decimal) can be applied, rounded to the rupee. There is no default percentage, and every figure stays editable while in draft.
  - **Spreading across months:** each head is `Equal monthly` (default), `Quarterly` (April, July, October, January), `Half-yearly` (April, October), `First month` (April) or `Month by month` (typed for each month, which sets the yearly total). Rounding remainders go to the last month that receives an amount.
  - **Approval:** an admin marks the draft `Approved` by recording who approved it (`Committee` or `General body`), the approval date (not in the future), an optional meeting or document link and an optional note up to 500 characters. Homeish does not check the approval. Approved figures are locked, with no undo; corrections use EXP-32.

The amount is spread equally from that month to March. A decrease may not exceed the head's current plan for those months. A move between heads is saved as one decrease and one increase. A mistaken change is cancelled with a reason (a move is cancelled as a pair), and cancelling is refused if it would leave a head below zero. Both stay in the history. A category created during the year has no budget until a change adds one. The original budget, every change and the current budget are always shown.
- `EXP-33` (P41.3) **Budget against actual.** A **Budget** tab in Accounts shows, for a chosen financial year and an approved budget, the actual figures from posted Accounts entries. Under proposed D-84, it also counts retained deposit deductions as non-cash Other income on the deduction date; this does not create a second cash entry. Held deposit receipts/refunds remain cash-flow movements, not budget income/expense. As on the Statements tab (EXP-21), reversals count in the month they happen and own-account transfers are excluded.
  - **Year summary by head:** original budget, changes, current budget, plan to date, actual to date, difference and % used. Heads with actual figures but no budget show "Not budgeted". The difference is shown in words: for money in, actual minus budget, so above budget is "Better than budget"; for spending, budget minus actual, so a negative figure is "Over budget".
  - **Month by head:** budget and actual for every month.
  - **Monthly cash flow:** money held at the start of the year (cash, bank and deposit accounts, as in EXP-21), any opening balances of accounts added during the year, money in, money out, net for the month and running net. Under proposed D-84, held-deposit receipts and refunds are shown separately but included as actual cash movements; retained-deposit income is a non-cash reclassification and is not included in cash totals. It is labelled as cash flow, separate from budget differences and from any surplus. Months not yet finished use the society's forecast setting: the budget (default), the average of the last three complete months (or fewer, saying how many), or no forecast. Every forecast figure is labelled "Estimate".
  - **Plan to date:** the current plan for the months up to and including the current month.
  - **Downloads:** admins and committee download CSV (protected against spreadsheet formulas) and PDF matching the screen. They are generated when requested and not stored.
- `EXP-34` (P42.2) **Warnings and projections** for spending heads in an approved budget:
  - **Projected year-end:** current yearly budget × (actual to date ÷ plan to date), rounded to the rupee and labelled "Estimate". It shows "Not available" when the plan to date is zero; for a finished year it shows the actual figure. Projected overrun (projected minus current budget) is shown only when positive.
  - **Burn rate:** actual to date ÷ plan to date, shown as a percentage.
  - **Warning levels:** `On track` below the society's Watch level; `Watch` at or above it; `Over plan` above 100% of plan to date, or when the projected year-end is above the current budget. The Watch level defaults to 90% and an admin can set 50%–100% in Accounts settings.
  - Warnings appear on screen only. There are no notifications, and nothing blocks, approves or delays spending.
- `EXP-35` (P41.3) **Budget summary for residents.** When the Accounts setting **Share budget summary with residents** is on (default on) and the year has an approved budget, residents (owners, tenants and family members with active access) see a **Budget** page. It shows each head's current budget, actual to date and % used, and totals for money in and spending. It never shows drafts, change details or reasons, warnings, projections, individual entries or payees, and has no download. When the setting is off or no budget is approved, the page says "No budget has been shared yet".
- `EXP-36` (P40.8b–P40.8c, proposed D-87; coding not yet approved) The fund report adds a derived **Reconciled** or **Needs review** status per bank account and month: Reconciled when the month is closed, the opening is not flagged, no suggested split is pending and every deposit is linked with no difference. Admins may type each month's bank-statement closing balance; the difference is shown but does not block, and edits need a reason and keep history. Each fund may have an optional target amount and date, showing progress, gap and a monthly amount needed labelled "Estimate". Labels are Negative balance, Below target, Target met and Behind schedule; there is no score. Admins download a CSV (audited); committee members view on screen.

- Budgets and changes are kept permanently, and every write is audited.

#### 5.10.3 Move-in / Move-out & Tenancy (`tenancy`) — P3-3

- `TEN-1` A resident or admin raises a move-in or move-out request with date, time window, and lift/loading-bay booking if the society uses it.
- `TEN-2` Tenant move-in requires a rental agreement and consent from any one active owner of the unit, with no admin bypass. Society-configurable police-verification proof is optional/off by default; it is required only when that society enables the requirement. No Aadhaar or other government ID copies may be collected (D-50).
- `TEN-3` Move-out shows a dues clearance check from `billing` when enabled. Any positive outstanding unit balance blocks the normal completion and NOC path; the P51/D-78 conditional handover may proceed only through its separately approved evidence, party-consent and admin-approval rules, with a fresh dues recheck. A failed check blocks for retry. When Billing is disabled, explicitly show **Not checked** and allow the applicable workflow without claiming clearance. An admin issues the NOC PDF. There is no move fee or deposit in this version (D-50, amended for new P51 issues).
- `TEN-4` Approval schedules the move and notifies guards; it does not change occupancy or access. An admin confirms actual completion to atomically add or end the tenant occupancy in Core. Use existing Core invitations, but do not activate the new tenant occupancy before completion. No backdated requests initially; move-out needs no separate owner consent (D-50).
- `TEN-5` In-app agreement-expiry reminders to owner and admin at 30 days, 7 days and expiry. Reuse an existing amenity booking when applicable; do not automatically reserve a lift/loading bay (D-50).
- `TEN-6` P36 summarizes actual move, agreement expiry, required proof and NOC information in existing authorized private move details. A completed historical move is not proof of current occupancy. Committee and guard schedules keep their existing projections; no new identity, agreement or proof fields are exposed there.

**P51 and P35.10–P35.12 transfer and clearance (D-78 — implemented, verified and on beta/testdb 2026-11-22).** TEN-7–TEN-11 are implemented in the existing `tenancy` module. TEN-9 replaces TEN-3's no-override rule and D-50's one-year deletion for newly issued certificates in this scope; existing NOCs retain their original meaning and retention. Nothing in it pays, waives, moves or deletes money owed, and nothing changes Core ownership or occupancy beyond the existing TEN-4 move completion. A society admin acknowledges a warning once per society before using transfer cases, conditional handover or the new certificates. The warning says these records are not legal advice, are not proof of transfer of legal title, and do not replace checking the state co-operative act or the society's bye-laws. Owner UAT, qualified legal wording review, main release and live enablement remain pending.

- `TEN-7` Admins record owner sale/transfer cases for a unit. The outgoing party is one or more current active owners. The buyer is a typed name with optional phone and email, optionally linked to an invited member. Each case also records the received date. Stages move forward only: Received → Documents checked → Committee decision → Dues cleared/handover agreed → Completed, or the case ends as Rejected or Withdrawn with a reason. Each stage records its date, and the screen shows elapsed days. A case is an application tracker only. Completing it does not change who owns the unit in the app, and admins still change Core ownership separately.
- `TEN-8` Admins record one committee decision per case: Approved, Approved with conditions, Rejected or Deferred. Each decision has a resolution reference and date, an optional link to a P23 meeting, and conditions, each with a responsible party, follow-up date and done flag. There are no automatic reminders. A Rejected decision ends the case as Rejected. A case moves past Committee decision only with an Approved or Approved with conditions decision.
- `TEN-9` For both tenant move-out and owner transfer, Billing on and nothing owed counts as cleared. If verified money is owed, the case is blocked unless an admin approves a conditional handover. The handover covers either specific unpaid bills with their amounts (the default) or the unit's total outstanding balance, as chosen in Tenancy settings. It names the party who agrees to pay. For a tenant move-out, the required agreeing parties are the outgoing tenant and the unit owner. For an owner transfer, they are the seller and the buyer. Evidence follows the society setting: an admin note (the default), an uploaded signed agreement, or in-app consent from parties with an account plus an upload for anyone without one. At completion and at issue, dues are checked again. If more is owed than was approved, the action is blocked until a new approval is given. A failed check blocks for retry. With Billing off, the outcome is "Not checked", never cleared. Other open checklist items never block. A handover does not pay, waive or erase the unit balance, which stays with the unit under D-29.
- `TEN-10` Admins issue three certificate kinds. A **Clearance NOC** requires verified no dues. A **Conditional NOC** lists the outstanding amounts as at the check time, the responsible party, the approving admin and date, and the approval reference. A **Not-checked NOC** applies when Billing is off. Each new certificate gets a per-society, per-financial-year number (for example `NOC/2026-27/0001`) and records the issuing admin's name and typed designation, the purpose, the case or move, the parties, the unit and the dues snapshot. The exact PDF is stored and never regenerated or relabelled. A mistake is corrected by issuing a new number and marking the earlier one "Superseded", with a reason. A request is not an issued certificate. NOCs issued before this change keep their wording, missing number and D-50 deletion date.
- `TEN-11` Admins manage. Committee members read case stages, decisions and certificate numbers, kinds and dates, with buyer names but no buyer contact details, agreement files or certificate files. Parties see only their own case, its handover and its certificates: the outgoing owners, the linked buyer member, and for move-out the tenant and unit owners. Guards have no access. Transfer cases, handovers, agreement uploads and new certificates are kept permanently, and edits keep previous values. Uploaded agreements are private PDF/JPG/PNG files of at most 5 MiB each.

**P52 tenancy additions (D-79; implemented on beta/testdb):**

- `TEN-12` Existing P18/Core records remain authoritative. Show derived move progress and a checklist view without duplicating occupancy, tenant identity or deposit records.
- `TEN-13` Optional verification tracking is off by default and stores `pending`, `verified` or `rejected`, plus date and reference only. Agreement type (`rental`, `leave_and_licence`, `company_lease`, `paying_guest` or `other`) and dates may be recorded with the existing P18 move; no full identity copies are collected, and metadata does not establish legal compliance. P18 access and retention continue to apply.

**P18 privacy and NOC policy (D-50, approved 2026-11-15; amended by D-78 for new P51 certificates):** private PDF/JPG/PNG uploads, at most 5 MiB per file, readable only by the tenant, active unit owners and admins. Committee is read-only for request status, not tenant files; guards see unit/date/time/status only. Delete tenant uploads and the original P18 NOC files one year after move-out, or after 30 days for rejected/cancelled requests. New P51 certificates follow TEN-10/TEN-11 permanent issued-document history instead, while old NOCs keep the D-50 deletion rule. Preserve Core occupancy history and financial records; existing audit retention applies. This is a narrow exception to the earlier police-proof storage exclusion, not permission to collect general identity documents.

**Approved NOC template:** "[Society] has no objection to the approved move-out of [resident] from [unit] on [move date]. Dues status at issue: [cleared as of timestamp / not checked because Billing is disabled]. Issued by [admin] on [issue date]. This records the society's move-out approval."

**NOC font boundary (owner-approved D-50 follow-up, 2026-11-15):** preserve all text supported by the installed PDF font, with canonical NFC normalisation; never strip accents or substitute question marks in names/labels. If a rendered field contains unsupported characters, clearly block NOC issuance before upload, without changing the saved names. Full-script font support remains a follow-up; no new dependency is authorised. This applies to the new tenancy NOC, not a behaviour change to existing Billing/Expense PDFs.

#### 5.10.7 Polls & Voting (`poll`) — P4-1

A native Homeish module ported from the Civic Pulse voting design (D-40). Civic Pulse remains a separate standalone product.

- `POL-1` PUBLIC polls: single or multi-select options, named responses visible to authorized management, a voter may change their selection until closing.
- `POL-2` PRIVATE elections: offices and candidates; only aggregate totals are ever stored or shown; participation is recorded separately from choices (application-level privacy, not cryptographic anonymity).
- `POL-3` Lifecycle: Draft, Scheduled, Active, Completed, Cancelled; the vote is frozen once active; deadlines enforced in the database.
- `POL-4` Entitlement: one vote per unit, cast by the unit's designated voting representative. Owners vote by default; tenant voting is a society setting, off by default (D-42).
- `POL-5` Results shown in-app after completion; management downloads PDF/CSV exports with the Civic Pulse privacy rules (PRIVATE exports list who voted, never choices).
- `POL-6` Zero duplicate, partial or post-deadline ballots, enforced atomically in the database.

**P22 owner decisions (D-60, approved 2026-11-16):** one vote per unit, cast by its representative. The default representative is the unit's active primary occupant if eligible, otherwise the earliest active owner; an admin or an active owner of that unit can choose another eligible occupant, and every change is audited. The voter list and representative names are frozen when a vote is scheduled or immediately activated. Tenant voting is a society setting (off by default, D-42); while a vote is a draft the admin can override it for that vote only, and the vote's value (the override, otherwise the society setting at that moment) is fixed when the vote is scheduled or immediately activated, together with the voter list; family members never vote. A vote covers the whole society by default, or blocks the admin chooses. Everyone living in a voting unit sees the vote and its permitted totals; only the representative votes. Residents see live totals of an open public poll; a private election shows turnout only until it completes. Private elections include "None of the above", which is counted but never wins. The admin can extend the deadline, complete early or cancel (from scheduled or open) with a required reason. Committee members see turnout counts while voting is open (never choices, never names) and results, roster and exports after completion; admins see who has voted once it opens. PDF and CSV exports are for admins and committee, completed votes only, with no email addresses; private exports list who voted, never choices. In-app notifications only: to the representatives when a vote opens, when results are available and when a scheduled or open vote is cancelled. Two years after a vote completes or is cancelled, per-person records (named responses, participation and voter list) are deleted; totals are kept. The load test target is 500 units with 100 concurrent voters.

**P46 official elections (D-81 — approved for local coding 2026-11-23; not released).** POL-7–POL-11 cover P46.1–P46.3 inside the `poll` module, which must be enabled. Official elections reuse the P22 secret-ballot engine as a separate election type; everyday polls, representatives, tenant voting, exports, notifications and the two-year P22 retention (D-60) are unchanged, and P23 meetings are unchanged. The app counts the votes; the returning officer declares the result. Homeish does not verify the society's law, bye-laws or authority, does not calculate legal deadlines and does not state that a notice, nomination or election is legally valid. Qualified local review is recommended but is not an in-app prerequisite (accepted risk, owner decision 2026-11-19). Admins manage; committee members read management views without the who-voted list; guards and housekeeping supervisors have no access.

- `POL-7` (P46.1) **Switching on and tracking official elections.**
  - Official voting is a `poll` setting, off by default. To switch it on, an admin chooses the society's legal type (`Apartment association` or `Housing co-operative`) and confirms: "Our registered rules allow online voting for committee elections and I am authorised to switch this on." No proof is uploaded. The admin, time and legal type are audited and shown on every election. It cannot be switched off while an official election is between Nominations open and Declared.
  - An election has a title, the snapshotted legal type, and posts, each with a name and number of seats. Stages: `Planning` → `Nominations open` → `Scrutiny` → `Candidates published` → `Voting` → `Counted` → `Declared` → `Closed`; `Cancelled` from any stage before Declared, with a required reason. A post whose accepted candidates do not exceed its seats is not balloted (POL-9); if no post needs a ballot, the election moves from Candidates published to Counted.
  - A schedule list holds activities with an owner, planned and actual dates, status (`To do`, `Done`, `Not needed`) and an optional note. Dates are the society's own plan: the app shows them and never derives legal deadlines or judges notice sufficiency.
  - Notices are links to existing Notice (`notice`) or Meeting (`meeting`) records, or Document (`document`) evidence, when those modules are enabled; there is no second notice system.
- `POL-8` (P46.1b) **Returning officer and other officers.**
  - Each election has at most one returning officer, required before Voting. They may be an active society member (any role) or an outside person invited by email for that election only. A returning officer can never be a candidate in that election. On accepting, they confirm "I am not a candidate and have no conflict of interest", which is audited. A resident returning officer still votes if they are their unit's voter.
  - Admins may also record assistants or observers by name and role only; they get no access and no contact details are stored.
  - An outside returning officer signs in with the existing email code. They see only that election's returning-officer screens, with no resident, billing or other society data, and are never a society member. Their access ends 30 days after the declaration, or when all disputes are closed if later. An admin can revoke or replace a returning officer at any time before Declared, with a reason.
- `POL-9` (P46.2) **Voter list and nominations.**
  - The voter list is built from units with at least one active owner. Each listed unit has one voter: the earliest active owner unless an admin names another active owner of that unit. An admin may remove a unit with a required reason (for example, unpaid dues under the society's rules); the app never removes units from billing data by itself. Tenants and family members never vote. Every change is audited.
  - The list, with voter and unit-label snapshots, locks when nominations open and cannot change afterwards.
  - Candidates always nominate themselves; nobody can nominate another person. Any active owner of a listed unit may stand for one or more posts during the nomination window set by the admin, and may withdraw before it closes.
  - A `poll` setting (off by default) adds supporters: when on, a self-nominated candidate may name a proposer and a seconder from the voter list, who each confirm in the app; nominations without supporters are still accepted. The candidate is never placed on the ballot by supporters.
  - In Scrutiny, the returning officer — or an admin while no returning officer is appointed — accepts or rejects each nomination with a reason for rejection. Accepted candidates are published to all residents.
  - A post whose accepted candidates do not exceed its seats is declared elected unopposed by the returning officer and left off the ballot.
- `POL-10` (P46.2b) **Voting, counting and declaration.**
  - Voting is online in the app only, for the locked voters, between admin-set start and end times. Each voter picks up to the number of seats for each balloted post, or "None of the above", once. Only per-candidate totals are stored, and who voted is stored separately (application-level secrecy, as POL-2; not cryptographic anonymity). Nobody, including admins and the returning officer, can see how a person voted.
  - The returning officer can extend voting or cancel with a reason; an admin can cancel with a reason before Voting. Counting runs automatically at close. NOTA is counted but never wins.
  - Ties are resolved by the returning officer, who records the method (for example, drawing lots) and a reason.
  - When one person wins more than one post, by default the candidate chooses which post to keep within 3 days; each other post then goes to the next-highest candidate for it who is not already elected, never NOTA. If the candidate does not choose in time, or the refill is tied or has no candidate, the returning officer decides and records why. A `poll` setting lets an admin make the returning officer decide in every such case.
  - The returning officer declares the result. A declaration is final in the app and is never edited; disputes are recorded beside it (POL-11).
  - Declared results and turnout are visible to everyone in the society. The who-voted list is visible to admins and the returning officer only; committee members see totals and turnout.
  - In-app notifications go to voters when nominations open and when candidates are published, voting opens and the result is declared; to named supporters for confirmation; and to a candidate who must choose a post.
- `POL-11` (P46.3) **Outside elections, disputes, costs and summary.**
  - Admins can record an election held outside the app (for example, on paper): date, posts, winners, optional vote counts and evidence linked from Documents. It is labelled "Recorded result — held outside the app".
  - Any listed voter may raise a dispute about an official election within the dispute window after declaration (a `poll` setting, default 5 days, 1–30). A dispute has text up to 2,000 characters and an optional private PDF, JPG or PNG file up to 5 MiB. Statuses: `Open` → `Under review` → `Resolved` or `Rejected`, with a required resolution note. Admins and the returning officer see all disputes; the raiser sees their own; committee members see counts only.
  - Admins may link posted Accounts (`expense`) entries to an election, when that module is enabled, to show its total cost. No entry, ledger or approval is created or changed.
  - An election summary on screen and as a PDF, generated on request and not stored, for admins, committee members and the returning officer, shows posts, results, turnout, timeline, dispute count and total cost — never who voted or how anyone voted.
  - Elections, voter lists, who-voted records, nominations, supporter confirmations, scrutiny decisions, tie and post-choice records, disputes and outside results are kept permanently. Ballot choices are never stored.

#### 5.10.8 Meetings & AGM (`meeting`) — P4-2

- `MTG-1` Admin schedules a meeting (AGM, SGM, committee) with agenda, venue/online link and notice period check.
- `MTG-2` Attendance by unit with a quorum indicator.
- `MTG-3` Resolutions can be linked to a `poll` vote when enabled.
- `MTG-4` Minutes and action items with owners and due dates; published minutes are stored in `document` when enabled.

**P23 owner decisions (D-61, approved 2026-11-16):** meeting types are AGM, SGM and committee meeting. By default AGM and SGM invite every active unit and a committee meeting invites the committee members; the admin can change the invitees of a meeting while it is still upcoming — whole society, chosen blocks, chosen floors or chosen units (unit meetings), or chosen committee members (committee meetings). Notice periods are society settings (defaults: AGM 14 days, SGM 7 days, committee 3 days); a shorter notice shows a warning only and does not block or need a reason. Quorum is a society setting shown as an indicator that never blocks: a percentage of invited units present for AGM and SGM (default 33%) and a percentage of invited committee members present for committee meetings (default 50%). Attendance is recorded per unit (per member for committee meetings): the admin marks it, and a unit may attend by proxy, recorded by the admin with the proxy's name and counted toward quorum. During a meeting the admin can open and close self check-in; while it is open, any active owner or tenant occupant (not family members) of an invited unit can mark the unit present once, and the admin can correct or undo any mark. The admin records each resolution's outcome (passed, failed or deferred, with optional for, against and abstain counts); when `poll` is enabled the admin can also create a pre-filled draft poll from a resolution or link an existing poll, and the completed poll's result is shown with the resolution. Admins and committee members can draft minutes; the admin can edit any draft, including one written by the committee, and only the admin publishes. Published AGM and SGM minutes are visible to residents of invited units; committee-meeting minutes are visible to admins and committee members only. When `document` is enabled, publishing also saves a PDF of the minutes in the document repository with the same visibility. Action items have an owner and a due date; a society setting decides whether owners can be any active society member (default) or only admins and committee members. Owners get a notification when assigned and one daily reminder while an item is overdue. Notifications are in-app plus push, to invitees when a meeting is scheduled, rescheduled or cancelled and when minutes are published. Meetings, attendance, resolutions and minutes are kept permanently as society records.

- `MTG-5` (P43.5, owner decision 2026-11-21) Admins and committee members see a read-only **Meeting summary** for the last 6 months, the last 12 months or the current financial year: meetings scheduled, held and cancelled; quorum met; average attendance; resolutions by outcome; action items open, overdue and done; held meetings whose minutes are not yet published; and each person's open and overdue action items with the next due date. It is factual only — no score or ranking. A headline tile also appears on Analytics.

**P45 requirements (MTG-6/7; implemented on beta/testdb 2026-11-22; owner UAT and live enablement pending):**

- `MTG-6` Admins may give each agenda item an optional duration of 1–1,440 minutes. When a meeting start time is set, the app derives advisory item start/end estimates in agenda order. A blank duration leaves that item's end and all later item times unknown; without a meeting start time, no estimates are shown. Estimates never change the scheduled meeting time, block scheduling, or claim legal sufficiency or statutory timing.
- `MTG-7` Admins manage society-shared agenda templates with an ordered list of up to 50 titles, optional descriptions and suggested durations, tagged for one or more meeting types (AGM, SGM, committee). Admins can filter templates by the meeting type, apply one to a draft as an editable copy, and edit or archive/restore templates. If the draft already has agenda items, replacing them requires confirmation. Later template edits or archiving never change agendas already copied into meetings. Committee members remain read-only and cannot manage or use these templates.

#### 5.10.9 Vendors & Purchase Approvals (`vendor`) — P4-3

- `VEN-2` Purchase request with up to several quotes; approval by a society-configured number of committee approvers.

#### 5.10.14 Major Repairs & Redevelopment (`major_works`) — P50

**P50 major repairs and redevelopment (D-82 — implemented and locally verified 2026-11-23; not released).** MWK-1–MWK-8 cover P50.1–P50.6. This is a new optional module, off by default. It needs no other optional module and links to Accounts (`expense`), Vendors (`vendor`), Meetings (`meeting`) and Polls (`poll`) only when those are enabled. Admins change records. Committee members read every record and score quotes. Residents see only the repair-project list (MWK-1) and, for owners, their own unit's consent status (MWK-7). Guards and housekeeping supervisors have no access. Homeish never approves work, creates a bill, levy, receivable or Accounts entry, verifies or endorses a developer, or states that a legal consent threshold is met. Qualified local review is recommended but is not an in-app prerequisite (accepted risk, owner decision 2026-11-22).

- `MWK-1` (P50.1) **Repair projects.**
  - A project has a title (up to 120 characters), location, category (the EXP-30 list), priority (`Low`, `Medium`, `High`, `Urgent`), estimate, planned start and end dates, actual start and end dates, progress % (0–100) and notes up to 2,000 characters. It may link to the EXP-30 forecast item it started from.
  - Status: `Planned` → `Quoting` → `Approved` → `In progress` → `Completed`; `On hold` from Quoting, Approved or In progress and back; `Cancelled` from any status before Completed. On hold and Cancelled need a reason.
  - Moving to Approved records the approval the society gave elsewhere: an approving body (`Committee`, `General body`, `Other`), date and an optional link to a passed Meetings resolution. The app records it and never approves anything itself.
  - Residents (owners, tenants and family) see each project's title, location, status, progress and planned dates — no money, quotes, audits, files or notes.
- `MWK-2` (P50.1) **Budget and spend.**
  - Each project has a budget source. `Typed` (default): the admin types the approved budget. `Linked sanctioned work`: the admin links one P40.4 sanctioned-work record (EXP-15), whose amount becomes the budget. Switching keeps the typed amount in the history, and the screen shows any difference.
  - Spend so far comes only from posted Accounts entries. In Typed mode, admins tag posted expense entries to the project. Tags across projects cannot exceed an entry's amount, and reversals reduce them. In Linked mode, spend is the sanctioned work's linked spending, and any project tags are kept but not counted.
  - When Accounts is off, the budget still shows, and spend shows "Not available". Overspend shows a warning and never blocks anything.
- `MWK-3` (P50.1b) **Structural audits.**
  - Admins record each structural audit: date, auditor name, findings summary up to 2,000 characters, rating (`Fine`, `Minor repairs`, `Major repairs`, `Unsafe`), an optional private report (PDF, JPG or PNG, up to 10 MiB), repair status (`Not needed`, `Pending`, `In progress`, `Done`) with optional linked projects, and the next due date.
  - Admins get an in-app reminder 30 days before the latest audit's next due date, and once on the day it becomes overdue. Audits are kept permanently. A wrong audit is voided with a reason, never deleted.
- `MWK-4` (P50.2) **Quotes and committee scoring.**
  - A project holds up to three quotes. When Vendors is enabled, the admin may link one vendor purchase request, and its live quotes are shown (P24); otherwise, or in addition up to three in total, the admin types quotes: vendor name, amount, scope note and an optional private file. Each quote has a "Like-for-like scope" tick. The app shows the lowest, the highest and each quote's % above the lowest.
  - Admins and committee members set 2–8 criteria with whole-number weights totalling 100, until the admin opens scoring; the criteria then lock. While scoring is open, each admin and committee member privately scores each included quote 0–10 per criterion and may change their scores. After the admin closes scoring, everyone with access sees each quote's weighted average (0–10) and how many people scored. Individual scores are never shown to anyone.
  - The app never labels a winner or ranks quotes as a recommendation. The admin may leave a quote, or the whole project, out of scoring with a reason. The admin separately records the chosen quote, the reason and an optional resolution link.
- `MWK-5` (P50.3) **What-if funding scenarios.**
  - Admins create named scenarios for a project: the amount to raise (typed, or the project's estimate or budget less a typed or chosen-fund amount), and a split by unit area (`units.area_sqft`) or equal per unit across active units. Units without an area are listed, and the scenario stays incomplete until the admin fixes them or switches to equal. Amounts round to the rupee, and the rounding difference is shown.
  - Admins and committee members see scenarios; residents do not. A scenario never creates a bill, charge, receivable, notice, receipt or levy, and it is labelled "What-if only — not a levy".
- `MWK-6` (P50.4) **Redevelopment proposals.**
  - Admins record proposals: developer name, received date, stage (`Received` → `Under review` → `Shortlisted` → `Selected`; `Rejected` or `Withdrawn` from any earlier stage, with a reason), a decision due date, and offer terms: extra area %, monthly rent per unit, corpus per unit, timeline in months, bank guarantee amount and other terms up to 1,000 characters, each optional. Private evidence files (PDF, JPG or PNG, up to 10 MiB each) may be attached.
  - Offers show side by side, labelled "As stated by the developer — not verified by Homeish". Admins and committee members only.
- `MWK-7` (P50.5) **Consent and milestones.**
  - Each unit with at least one active owner has one consent status per proposal: `Pending`, `Consents` or `Does not consent`. The record shows how it was recorded (`In-app poll` or `Recorded by admin`), the date, who recorded it and an optional private signed-form file. Admins and committee members see all records; each owner sees only their own unit's status and method, never files or other units.
  - A `major_works` setting, **consent method**: `Poll answer counts as consent` (default) or `Admin-recorded consent only`. Before the first consent poll, or before switching to the poll method, the admin confirms once: "Our bye-laws and applicable rules allow this consent method, and I accept responsibility for it." The confirmation is audited.
  - When Polls is enabled, an admin can create a draft consent poll from a proposal. It is a named public poll (POL-1) with the options "I consent" and "I do not consent", for the whole society, with tenant voting off for that poll; it follows the normal poll schedule and notifications. When it completes under the poll method, each voting unit's answer fills that unit's consent record unless an admin-recorded entry already exists. Under the admin-recorded method, the answers are shown beside the tally as "Indicative only" and never change a record. Copied answers stay after the poll's two-year purge (D-60).
  - The tally shows counts and % of eligible units for each status. It never says that a legal or statutory threshold is met.
  - Milestones are a dated checklist per proposal: title, planned date, actual date, status (`To do`, `Done`, `Not needed`) and a note.
- `MWK-8` (P50.6) **Summary and retention.**
  - An on-screen summary for admins and committee members shows, for each active project, budget against spend (MWK-2), progress, delay (past the planned end and not completed), overdue audits and the number of open proposals by stage. It never shows consent details or files, adds no P27 metric and has no download.
  - Residents (owners, tenants and family) get a simplified summary: the MWK-1 project list with each project's status, progress and planned dates, and no money, audits, quotes, delays or redevelopment information.
  - Projects, audits, quotes, scores, scenarios and their history are kept permanently. An admin may archive a proposal in Selected, Rejected or Withdrawn; its consent records, milestones and files are purged by the daily job 8 years after archiving, and the purge is audited with counts.

## 6. Core User Journeys (End-to-End)

1. **Society Onboarding (Developer → Admin)**: Developer creates society → enables modules → creates first Admin by email → Admin signs in, sets up blocks/units (CSV) → adds guards → invites residents.
2. **Resident Onboarding**: Receives email invite → email code login → confirms profile and unit → sees home with enabled modules.
3. **Visitor at the gate**: Guard logs visitor → resident notified → approve → entry → check-out.
4. **Monthly billing cycle**: Admin generates bills → residents notified → pay via UPI (admin confirms) or offline → receipts → reminders → late fee → dashboard review.
5. **Raise & resolve a request**: Resident raises → admin assigns → status updates → resident confirms → rating.
6. **Debugging an issue**: Resident sees error with reference ID → shares with developer → developer finds it in Log Viewer → resolves/marks.
7. **Module toggle**: Developer disables `delivery` for Society X → guards/residents no longer see it → data retained → re-enabled later with history intact.

### 8.1 Roles

| Role                            | Scope         | Notes                                                                                                  |

A user can hold multiple roles within a society (e.g., committee + resident). Permissions are the union.

**Returning officer (P46, D-81 approved for local coding):** not a role. It is an assignment to one official election, held by a society member or an outside person invited by email for that election. It grants only that election's nomination scrutiny, tie, post-choice, declaration, who-voted and dispute screens (POL-8), and an outside returning officer gets no society membership or other data. Owners vote and nominate only when they are the listed voter or an active owner of a listed unit (POL-9).

### 10.2 Data Rules

- `DAT-1` Every tenant table has `society_id`, created_at/by, updated_at/by.
- `DAT-2` Money stored as integer minor units (paise) with currency code.
- `DAT-3` Ledger and payment records never deleted or edited; reversed by new entries.
- `DAT-4` Visitor/delivery/staff-entry records retained for **[A-28]** 1 year by default (configurable), then anonymized/archived.
- `DAT-5` Files (photos, PDFs): max 5 MB per file, allowed types JPG/PNG/PDF, stored in object storage with access via signed, expiring URLs, scoped per society.
- `DAT-6` Personal data (phone, name, photo, vehicle) accessible only per role matrix; masked in logs.
- `DAT-7` Unit and user deactivation = soft delete; history preserved.
- `DAT-8` Data export/deletion request process for a user is handled by developer on request (MVP, manual). **[A-29]**
- `DAT-9` Data initially loaded via CSV: Units (block, number, floor, type, area) and Residents (name, email, phone optional, unit, relationship, role). Validation errors reported per row, with a downloadable error report.

## 13. Edge Cases and Business Rules (explicit)

- A unit with no active approver: visitor entry shows "No resident to notify"; guard follows `VIS-4` policy.
- Multiple approvers respond simultaneously: first response wins; the others see the final status.
- Same email, multiple societies: allowed; roles are per society.
- Resident leaves (move-out) with dues: admin can still view/collect dues; the ledger stays attached to the unit; new occupant does not inherit individual-level history. Outstanding unit dues are billed to the current owner. **[D-29 — Approved 2026-11-09]**
- Bill generated twice for the same period: blocked (`BIL-2`).
- Resident submits a UTR the admin cannot find in the statement: admin rejects with a reason; resident may resubmit. Same UTR submitted twice: blocked (`BIL-16`). Resident pays the wrong amount: admin confirms the actual amount received (partial/advance rules `BIL-8`, `BIL-9`) or rejects with a reason.
- Module disabled mid-flow (e.g., visitor pending): pending items freeze; guard sees module-disabled; on re-enable they expire if past timeout.
- Deleting a unit with history: blocked; deactivate only.
- Time zones: use IST for all displays and business dates, regardless of browser or server timezone. Preserve the exact instant of previously recorded timestamps. Other zones are a future Pro feature. **[Owner-approved 2026-11-21]**
- Pre-approval code reuse: single-use by default; multi-use within window optional per invite (**[A-30]** MVP single-use only).

D-84 proposes held-deposit cash movements in P16 and a separate income reclassification for amounts retained; it does not add a full liability ledger, payment gateway or automatic refund. This is a narrow proposed D-39 exception, with accountant review recommended before real use. A forward-only migration, P16/P41 report changes and private resident-authorized evidence are proposed; no code, hosted migration or live use is approved.

**D-85 — Unit handover: P36.7a–P36.7b (Proposed 2026-11-23; coding not yet approved):** Adopts CORE-32. Handover covers tenant move-in, tenant move-out, owner transfer and standalone checks. Admins record and close; the society edits a checklist template that is copied into each handover. Meter readings reuse P26 by reference. Photos are optional and private. Party acknowledgement is optional and never blocks. An unfinished handover only warns when a move-out or P51 case completes, and the override is audited. Records are permanent and never change occupancy, ownership, money or NOCs.

**D-86 — Compliance register and official case log: P43.4 and P44.5 (Proposed 2026-11-23; coding not yet approved):** Adopts CORE-33 and unblocks DOC-8 on an accepted-risk route: a once-per-society acknowledgement that the app is not legal advice or certification, with legal review recommended rather than required. P43.4 keeps its 2026-11-21 scope; P44.5 is admin-only with in-app reminders off by default at 30 and 7 days. Both are kept permanently by default; a shared **Settings → Data cleanup** tab lets admins opt in to deleting completed or closed items older than 1–20 years with their files, audited.

**D-87 — Fund reconciliation and targets: full P40.8 (Proposed 2026-11-23; coding not yet approved):** Adopts EXP-36: derived Reconciled/Needs review status, typed monthly statement closing balances (non-blocking, reasoned edits with history), optional fund targets with an "Estimate" monthly amount and plain labels without a score. Admins download CSV (audited); committee views on screen. Accounting meaning stays with the society's accountant.

**D-88 — Bill email and sharing: P37.5 (Proposed 2026-11-23; coding not yet approved):** Adopts BIL-27. Automatic bill email on publish (summary, sign-in link and bill PDF attached) is on by default, including for existing societies, and can be switched off by an admin. Sharing uses the phone's share menu or a click-to-chat/email link started by the user; the app audits only that sharing started. D-06 is unchanged and no provider is added.

**D-89 — Interest on overdue bills: P38.1 (Proposed 2026-11-23; coding not yet approved):** Rewrites BIL-18 with the owner's chosen rules: off by default, once-per-society acknowledgement, late fee/interest/both, a yearly rate up to the 24% app limit with history, simple daily interest on regular and utility bills from the effective date, one monthly interest bill per unit for the previous month, never recalculated and waived only through BIL-4. The owner chose to plan this without the earlier required accountant/legal review; that review remains strongly recommended before real use.

**D-90 — Future regional interface languages (Owner-directed 2026-11-23; deferred):** Gujarati, Kannada, Tamil, Telugu and Bengali (Bangla) are possible future Pro languages if societies show sufficient interest and willingness to pay. This decision authorises recording the idea and staging its licensed font assets only. It does not approve translations, UI availability, pricing, a plan, a phase, application/schema changes or a launch commitment.

## 18. Glossary

- **Society/Apartment**: a residential community managed as one tenant.
- **Unit**: a flat/house.
- **Primary contact**: main person responsible for a unit.
- **Approver**: occupant authorized to approve visitors/deliveries.
- **AMC**: Annual Maintenance Contract.
- **Module**: independently enableable feature area.
- **Reference ID**: code shown on an error to find its log entry.
